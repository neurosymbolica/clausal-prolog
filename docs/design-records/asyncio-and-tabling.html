Asyncio and Tabling

Running Prolog queries on Python's asyncio event loop, and the rules that keep SLG tables sound when queries interleave, get abandoned, and die.

01

The model

A query waits on the outside world without the program saying anything about it. How the query is driven decides what a wait does.

A predicate that needs to wait (a timer, a network call, a model, a person) calls await_only(awaitable) from ordinary synchronous code. The library predicates sleep/1, await_value/2 and await_each/2, and any adapter built with async_predicate, do exactly that. What happens next depends only on the driver:

One program, three drivers
DriverWhat a wait does
asolve, aonce, acallSuspends this query; the event loop runs other tasks and queries meanwhile.
solve, the CLI, the REPLBlocks on a private per-thread loop. The program runs unchanged.
solve inside a running loopRefused: permission_error(await, synchronous_query, _), instead of freezing the loop.

So asynchrony does not spread up the call chain the way async def does in Python. Nothing in a Clausal Prolog program is marked async, and backtracking works across waits: await_each/2 turns an async iterator into one solution per item, pulled only when backtracking asks for the next.

There is no scheduler of our own. The loop is Python's standard asyncio loop, so timeouts, cancellation, racing and task groups are asyncio's, and a proof can wait on any async Python library directly.

02

How it runs

Clausal's engine is a generator trampoline: compiled predicates are Python generators driven by a flat loop, partly in C. The flat loop alone would make a native await easy, because a predicate could yield an "await this" request to the root driver. But several constructs run their own nested synchronous drive loops: findall/3's inner goal, negation, once/1, lambda bodies, tabling's spawns. A request yielded inside one of them never reaches the root. We prototyped the native route: it worked at the top level and hung inside findall.

So asolve runs the ordinary synchronous engine inside a greenlet, the technique behind SQLAlchemy's asyncio support. await_only switches from the query's greenlet to the greenlet running the asyncio task; that one awaits and switches back with the result. Every frame between the two, Python or C, stays suspended as it is, so no engine path had to learn about waiting.

A greenlet runs on its thread's own stack and copies its slice to the heap when it switches out, so recursion depth is the same as in plain code. Switching costs time in proportion to the stack depth at the wait:

The trampoline keeps ordinary recursion off the Python stack, so a wait is usually shallow. Depth comes from nesting the trampoline cannot flatten: findall inside negation inside once, deep ++ escapes, recursive Python adapters.

03

The contract

  • Interleaving. Each query has its own trail and its own tabling bookkeeping (leader stack, drive episodes, spawn depth: thread-locals that are swapped in per query). Queries interleave only where one waits.
  • Shared database. An assertz by one query is visible to another after the first one's next wait.
  • Errors. An awaitable that raises surfaces as an error term, catchable with catch/3.
  • Cancellation. Cancelling the task raises CancelledError inside the query at its wait; the query unwinds and setup_call_cleanup/3 cleanups run, including ones that wait. catch/3 cannot swallow a cancellation.
  • Stopping early. A break out of async for does not close an async generator; call aclose(). The seam compiler does this itself for a for over --goal in an async def.
  • Waits that may not happen. A synchronous query inside a running loop, and code the garbage collector runs inside a query (an abandoned query's cleanup), are refused with permission_error(await, synchronous_query | finalisation, _).
04

Tables shared by interleaved queries

SLG resolution assumes one search builds each table. Interleaving breaks that assumption in five distinct ways, and each needed its own rule.

A synchronous query runs to completion before the next starts, so a table under evaluation belongs to whoever is running. An async query can be suspended at a wait, or between answers it is still streaming, with tables half-built and visible to every other query. It can also be abandoned without being closed, or die (its event loop closed, its driver garbage-collected) without finishing them. These are the rules, as implemented in the "Ownership" section of clausal/logic/tabling.py:

Rule 1Every table records its owner

An entry records the query leading it; synchronous queries have owner None, so in the synchronous world every rule below is a no-op.

Rule 2A foreign table is never touched

Foreign: owned by another query that can still resume, or on a synchronous leader stack that the running async query swapped out (an async query run from inside a synchronous one's consumer). It is never consumed, re-led or completed; reaching one raises permission_error(access, tabled_evaluation, P/N). Consuming a partial answer set silently loses answers, which is the bug this rule closed.

Rule 3An abandoned table is rebuilt, never resumed

Abandoned: still evaluating, not ours and not foreign, because its query is dead. Its partial answers, conditions and SCC dependencies describe a search that no longer exists. A new lead starts from a fresh entry. Store-wide passes (SCC completion, the negation variant scan) leave it alone; completing it would freeze its partial answers for good.

Rule 4Lead tokens guard every repair

Every lead and re-lead sets a fresh token on the entry. A leader frame's abnormal-exit repair (drop the half-built entry, release its consumers) and its leader-stack pop act only while the entry is still its lead. A re-lead reuses the entry object, and a dead query's frames can be finalised by the garbage collector long afterwards, so identity alone is not enough.

Rule 5Death is noticed anywhere, acted on at safe points

A query is live while it can resume: not closed, its driving async generator still exists, its event loop not closed. When the driver is freed unclosed, a weakref callback only queues the query, because the cyclic GC may run that callback in the middle of another query's loop over a table store, or in another thread. At the next safe point (the start of a tabled call or tabled negation, or an async query switching in) the dead query's half-built tables leave the store and its generator is finished under its own engine state.

Lesson

Five of the seven blockers had the same shape: some code path met a table that another, now dead, query had left half-built. Patching paths one at a time found the next path each round. What ended it was giving death a single, explicit handling point (rule 5), with the per-path guards kept as a second line.

06

On a WAM

Notes for an implementation in a WAM-based Prolog such as Scryer. They are our reading, not a measurement of any other system.

DifferentThe engine side is easier

Greenlets were needed only because a wait can happen under host-language frames (nested Python drive loops, C). A WAM keeps a query's continuation in its own registers and stacks, so a builtin can stop the run loop at a wait and the host can resume it later. There is nothing to copy and no switch cost that grows with depth.

Carries overThe semantics

The driver decides what a wait does; the program never marks anything async; backtracking works across waits; a synchronous query inside a running loop is refused rather than allowed to block it.

Carries overThe tabling rules

Any system that lets queries interleave over shared SLG tables meets the five problems of section 04, whatever the engine: a half-built table seen by another query, abandoned evaluations, repairs racing re-leads, store-wide passes over other queries' tables, and deciding when a query is dead. The fixes are engine-independent.

Carries overCleanup ordering

Most of our late bugs came from clean-up running at the wrong moment, under the wrong query's state: garbage-collector finalisation of abandoned frames. A system with explicit, eager cleanup of abandoned queries avoids that whole class.
