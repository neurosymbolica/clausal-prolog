Terms as Tuples

Retiring the per-predicate class, and what it revealed about how one module reaches another.

branch feat/iso-l3-lowering-2026-09-14 head 34066f5e landed nothing engine gate 0 new oracle gate went red
01

The spine

One move, repeated at three levels: collapse incidental Python object identity into explicit keys and immutable data.

Terms stop being generated class instances and become functor-first tuples — S-expressions, with atoms as 1-tuples so an atom is distinguishable from a string in argument position and shaped like the arity-0 compound it is. Predicates stop being classes and become Database rows keyed (functor, arity). And imports stop being Python attribute references and become row sharing.

The reasoning is the same each time. Prolog needs immutable compounds; the only things that change are variables. Tuples are immutable and CPython gives them fast paths — the C do_unify already has a native functor-first path, which is why the class is a cost, not a feature.

One honest counterpoint: a __slots__ instance is 48 B against a tuple's 64 B, so per-term memory slightly favours the class. It is swamped by the per-class fixed cost and by the construct and unify gaps.

02

Four representations, going to one

Today four term shapes coexist and do not interoperate. A class instance, a functor-first tuple and a Compound are pairwise unequal and do not unify. Conflating them has been the expensive mistake in this lane.

Compound is not needed — and the tuple strictly dominates it

Compound is a dataclass of functor: str | Var, args: tuple and a source position. The one capability that could have justified keeping it — a variable in functor position — measures the other way round.

Compound.__unify__ refuses to bind an unbound functor variable on purpose — the “deref-only floor”. The tuple path binds it. So the tuple is not merely equivalent; it is more expressive on the only axis where Compound looked richer.

The single open item in removing it is _position, the source span it carries for diagnostics and a tuple cannot. That is a diagnostics question — a side table, or positions kept on the clause rather than the term — not a representation one.

Which tag marks a tuple that is data, not a compound

Slot 0 of a term is the functor. A Python tuple arriving as data needs a tag there, because its own first element could be anything. Today that tag is the tuple type object — which cannot be marshalled, and that single fact is the whole reason emitted code has to reach the tag by name through a $cells namespace instead of folding it into a constant.

'()' has neither problem — and it is not a new convention, it completes an existing one. ISO gives each bracket syntax a reserved quoted atom as its functor, and this tree already implements two of them:

So '()' is the third member of a family, in the shape the engine already stores the first two. That it can be written as a quoted atom is the same property '{}' and '[]' have — a feature rather than a collision. '()'(1, 2) is valid ISO, which gives tuple-data a portable spelling with no new syntax and lets a .pl file carrying one load in Scryer and Trealla.

The one cost, stated plainly: the atom '()' stops being available as an ordinary atom — the same trade '[]' already makes. It is free today: no uses in engine Python, no .clausal file, no test.

And the corpus cost is zero. Swept: no corpus file names TUPLE_TAG, $cells or is_cell, or matches slot 0 on a type. Corpus source writes (1, 2) and the compiler applies the tag, so a re-tagging is compiler-internal. That was the one number between this recommendation and a decision.

03

The seam already speaks tuples

The Python seam does not need predicate objects coming out of it, and it has not needed them for a while. Goal-position -- already calls and constructs in the target representation, resolving through the module's Database rather than any module-level binding.

if --goal(X): and for a, b in --goal(A, B): lower to exactly this and export answers as ordinary Python locals — transparent variable handling, with the goal's variables becoming names the host function can read. The calling convention is --, not m.some_pred.

Retracted

An earlier draft of this record recommended keeping one generic callable handle at module level, so Python could still call and construct. That was argued from 209 object-shaped accesses in the engine's own tests without checking what the seam had already replaced them with. The module-level name should be the atom ('some_pred',) and nothing else. The 209 are a migration to an idiom that already exists.

04

What crosses the seam

Arbitrary Python objects should not become terms: marshalling does not work on them, and keeping them out is safer, cleaner and faster. The refusal in the tree today sits on one specific line, though, and there turned out to be three lines, not one — which is what the ruling below had to settle.

The compile-route refusal comes from term_to_ast_expr: once_bind hands the goal to solve(), which lowers it to AST — it treats a goal as source to compile, and an arbitrary object has no literal AST form. The runtime route is a different mechanism entirely, and terms_to_ast.py's own comment relies on it: a bound variable whose value “has no literal lowering (e.g. a datetime.date produced by an earlier goal)” is handled by referencing the variable.

Ruled The values that seemed to need an exception get an encoding instead. A date is the term ('date', 2026, 9, 14); a decimal is ('decimal', M, E) — mantissa and a count of decimal places, so exactness and scale survive the round trip. The refusal stays exactly where it is raised today.

This removes the exception rather than accommodating it. Both encodings are ordinary functor-first terms and both are marshal-clean, so there is no second class of value to declare, no vocabulary to maintain, and one rule covers everything: a term is marshal-clean data, and a Python object is not a term.

It also settles the two inconsistencies by deletion. datetime.date no longer needs to pass the compile route, because a date is no longer a Python object; Decimal's refusal there stops being a gap and becomes the rule. And with nothing legitimate left on the runtime object route, the refusal can eventually be made uniform across both — a separate change with its own blast radius, since existing code may lean on it.

05

§4 answered: what binds at module level

The question the removal was blocked on. It turns on one fact: -import_from is getattr, and the importing Database has no record of the import at all.

The entire import relationship is one Python object reference in module_dict. So there is nothing to reroute to — the relationship has to be created. That single absence explains every cross-module oddity found in the site pass: the _tabled_home_db stamp, _te_predicate_nodes, the double-indexed import origins, and io.py's recorded bug note that “the class knows its own row; the name does not”.

q1-import_from → a shared rowMeasured feasible

Plant the exporter's row in the importer's table under the importer's own spelling. Database.row() consults _rows first, so it is a key insert, not new machinery. Probed with controls: clauses and dispatch become reachable through the importer, an unplanted key stays None, and is_defined still reports on the importer's own storage.

The alias problem disappears — a key has no intrinsic name, which is exactly why alias(edge, link) is hard today. row.db is not self becomes the ownership test. Every class-only attribute gets a row home, and _tabled_home_db is deleted outright because a row already knows its database.

q2Export lists stay advisoryMeasured

A -private name absent from the -module list is still importable today, and still answers. Nothing is being enforced, so converting exports to a (functor, arity) set translates nothing. Record the set; rule on enforcement separately, because turning a silent success into a load error across an unmeasured corpus is its own decision.

q3A module-level name is ABSENTRevised

Ruled first as “the atom”. Measured later: the spec's other branch — absent — costs less and is the cleaner end state. A logic module is a plain Python module, so a PEP 562 __getattr__ fires on a MISS and resolves the name from its Database row.

A miss-only hook serves every REACH and cannot ENUMERATE, and that is the whole distinction. Attribute access, getattr by literal and by variable, hasattr, and from domain import pred all keep working untouched; only vars(m), dir(m) and name-discovery loops break.

Enumeration sites: 3 in the engine (each already headed for “enumerate the db's rows”), and zero in the 82 sealed harness bodies. So q3 costs one hook plus a __dir__ — not the ~655 site edits an earlier count in this record claimed.

q4The type testMeasured

Answered by the census and the per-site pass: 431 references classified, category A is 50 sites, 14 of which are not category A at all. Five of those hoist type(x) into a local, so separating “is this a predicate” from “is this a term” has to be done on the dataflow, not on the line.

06

The class does hold state of its own

The removal spec argues the class holds nothing — its state reads through to a PredRow, which is itself a facade over the Database. That is true of nine attributes and false of six.

Two of them are carriers: stamped on the class precisely because the class is shared across -import_from while a row belongs to one database. They are not leftovers, they are the workaround for the absence in §5 — which is why answering q1 dissolves them instead of migrating them.

07

The cut barrier

Cut-free forever is a property of .clausal, not of the engine.

.pl may carry cut and the rest of ISO. Clausal code must not be able to call into code with cuts — not even load it. A cut-free .pl file must run unchanged when renamed .clausal. The seam has no cuts and keeps none. The purpose is to guarantee monotonicity, because .clausal is the target of formalisation into ontologies.

  • One front end, two suffixes. “Rename it and it runs” is only true if both read through L3; the suffixes then differ by a gate, not a grammar.
  • Purity is statically decidable — the reader sees ! in a body — so it is a gate rather than a judgement.
  • But purity is a property of the import closure, not of a file. Pure A imports pure B imports impure C, and A can reach a cut. A module carries a purity bit that is the AND of its own text and everything it imports. This is the part the plan does not say.
  • The enforcement point already exists. q1's plant is the one hook that sees “X depends on Y” with both modules resolved. Row sharing, export enforcement and the purity barrier are three jobs for one chokepoint.

Zero files have moved to .seam. .clausal cannot take on ISO syntax while 431 engine files — plus the corpus, which is not measured here — still hold Python-seam syntax under that name. The write-side flip is the prerequisite for the whole cut gate, and it has not started. It does not block L3, which targets .pl.

08

What the measurements got wrong

A green engine suite said the date change was safe. The oracle gate said otherwise on its first domain, and the difference between those two claims is the most useful thing here.

The claim behind the change was that the corpus never imports the date module and so could not be affected. The sweep was accurate; the claim generalised past it. The sealed scorer bodies are not in the corpus tree, they construct datetime.date and pass it into goals, and that is exactly the path the change closed. Five of the first six procurement scorers went scoreless; the sweep was stopped there rather than watching the same traceback fifty more times.

Four claims failed the same way in one day, and the cause is structural rather than careless. The sealed bodies are excluded from every other lane's census by the seal — one lane cannot read them, the exporter skips their directory, engine sweeps cover the corpus tree. So “the corpus costs nothing” is silent about the harnesses by construction, and that population exercises the engine more directly than any other.

Protocol Any sweep whose conclusion would cover the harnesses goes to the lane that owns them as a question, before it becomes a number. Most are one AST pass.

And state the glob in the sentence. “No .py file does X” is a fact; “the corpus does not do X” is an inference across a boundary, and the two read identically in a report.

One domain answered wrongly rather than failing

Migrating the harnesses' date constructions — rather than their crossings — returned framework_agreements at 1413/1423. Ten cases silently got a different answer instead of an error, because the harnesses do not merely pass dates to the engine: they compute with them in Python, and a term is a tuple with none of that API. That is the failure the whole oracle axis exists to catch, and it is why the remaining migration converts at crossings, where nothing downstream computes with the converted value.

09

The conversion registry

Two global dicts, no overriding: TO_TERM maps a class to the function yielding its term, FROM_TERM maps a functor to the function rebuilding the Python value. Each function knows its own components and decides what recurses — the date family moves its ints across untouched, the data tuple recurses because only it can contain anything.

There is no generic converter. An early cut walked __match_args__ and mangled a module-qualified functor for anything unregistered. The reason to delete it is not that it fails on date and Decimal, which report no match args — it is that a class's attributes may each need converting differently, and only that class knows how. A generic walk applies one rule to all of them, so it is not a fallback; it is a different, wrong answer that happens to typecheck.

The reverse direction earns its place immediately: round-trip tests pin that a Decimal keeps its scale (10.010 stays 10.010) and that an aware datetime keeps its offset — the two properties an earlier pass got wrong.

Reverted Hooking the registry to ++, so a Python value would convert automatically on the way in, failed at three insertion points. Wrapping the emitted call broke the seam's own passes, which pattern-match its shape. Wrapping the thunk left the shape alone but wrapped tuples the seam itself built. That is the real obstacle and it is a design question: ++ sits where both kinds of tuple are in flight and nothing in the value distinguishes them. The converters are callable today; only the automatic application is unresolved.

11

The one value that stays an object

quantity does not become a term. It gets a term form, and the two are converted explicitly.

Every other value in this record moved the same way: a date, a decimal, a rational stopped being a Python object and became a functor-first tuple. A quantity cannot, and the reason is not about representation at all. A quantity stands in for a number. It has to be an operand of #=/2 and of the CLP arithmetic, and a compound term is not a number. That is the line: a date is never an operand, so it could migrate; a quantity is too low-level to.

Demoted The argument this record would have led with — that a tuple's hash is structural and cannot be hooked, so a tuple quantity carrying a ratio would be two dict keys for one value while unification called them equal — is true, and it would have broken tabling, the query cache and indexing. But it is a corollary. The #=/2 argument holds even where hashing does not.

The boundaries that motivate the encoding are subinterpreters for or-parallelism, process boundaries, and Python's bytecode caches at compile time. Not same-interpreter seam crossings — a seam in one interpreter passes the object and needs no encoding, and naming the seam as the motivation was wrong. The .pyc boundary is what makes this a hard requirement rather than a nicety: marshal takes only the basic types.

Two things fall out of that table. It is the mappingproxy that blocks _dims, not the dict — so “a quantity is a true value, containing no other Python objects” is one rekey away from literally true. And Decimal and Fraction do not marshal either, which is why ('decimal', M, E) and ('rdiv', N, D) exist — so the ratio must be a term too, recursing through the registry exactly as the magnitude does.

Ruled A unit is unit(Ratio, Dimensions) — always unit/2. The ratio travels, not the name. Dimensions are dimensions(metre(1), second(-2)), sorted on emit — see below, where the stored map becomes a dict and the sort stops being an invariant. Dimensionless is the atom dimensionless.

The currency name was never at risk, and the reason is the one that looked like a problem. A currency is a self-keyed base dimension — pred._dims = {pred: 1} — so its name is already in the dimensions map. 1550.00 euro prints as euro because currency is not SI. What actually loses its name is a scaled unit: 5 kilometre is 5000 (metre) today, in the object, before any of this.

The two questions this closes Ruled
Does the named unit survive?No — the ratio does. Currency names survive anyway, as dimensions.
How is dimensionless spelled?The atom dimensionless — already a real unit predicate, already what str() emits so the value round-trips.

The rejected spelling was the more uniform one and that was argued away wrongly at first: ('dimensions',) and ('dimensions', ('metre',1)) share a functor, so one test recognises and one slice iterates, for zero and for N alike. Choosing dimensionless means the dimension slot carries two functors, and “the dims slot has functor dimensions” stops being free. One helper, used everywhere — not a branch copied per site. It is the same shape as the thirteen pair-before-compound sites in §08: a property that was free under one representation has to be written down under the next.

Ruled Conversion is explicit: quantity_number(QuantityTerm, Number). One relation, dialect-specific right side — Clausal binds the Python quantity; a Prolog with no units binds the number scaled to the standard unit for those dimensions. Where it is called depends on which boundary is being crossed, and is deliberately not fixed. This replaces a proposal, now withdrawn, that __unify__ should accept a written term and compare by value.

Nothing is lost, because the object had already normalised before the term existed. But if a quantity should also round-trip the unit it was written in, that is a change to the object — a third slot — not to the transfer form, and it is not ruled. It is the only thing these rulings leave open.

Ruled The dimension map is a plain dict inside and a tuple on the wire. The hashability argument that first chose the tuple was about a runtime term, and a quantity is an object — so it never reached the stored map at all.

So the dict is free, and the mappingproxy was the only thing blocking marshalling. Store the dict; have the dims property return a proxy view, so the immutability guarantee survives at the public boundary — __hash__ is computed from _dims, and a caller mutating it would silently corrupt an already-hashed value.

Withdrawn That a dict has no ISO spelling. It does: Scryer and Trealla both read {'metre':1,'second':-2} as {}(','(:(metre,1),:(second,-2))) — an ordinary term over {}/1, ,/2 and :/2. Measured on both.

Softened That the canonical sort is not optional. For Clausal-internal equality the dict is order-insensitive and the sort is unnecessary. It returns only on emit, because a curly term is a term over there — {metre:1,second:2} == {second:2,metre:1} is false in Scryer. That applies under either wire spelling, so it stopped being a point of difference.

The tuple folds whole into co_consts. The dict does not fold at all — the cache stores fragments and a recipe, and the term is rebuilt at every evaluation. Both code objects still marshal (163 vs 178 bytes), so the .pyc works either way; what differs is whether the finished value or the instructions to build it are what gets cached. It bites here because a quantity literal is read into an object at load, so the thing sitting in co_consts is the transfer term.

frozendict was considered and rejected. It is hashable, but it is not in the stdlib and not installed, and it would lose both properties at issue — marshal takes only the basic types, and a custom class folds into co_consts no better than a dict. It also solves a problem that is not there, since the stored map never needed to be hashable.

So the sort is skippable for the 60% of units carrying one dimension or none — every currency, every base unit — but not wholesale, because _merge_dims is path-dependent and two equal quantities would emit different terms. And the obvious len(d) > 1 guard costs more at n ≥ 2 than the sort it skips: about 17 ns per emit once weighted, on an operation that happens only at a marshal boundary. Sort unconditionally — not because the saving is unreal, but because it sits behind a branch, and a branch is the thing that later gets copied to a site where its premise does not hold.

Measured The sort is impossible today. sorted(d.items()) raises TypeError: '<' not supported between instances of '_UnitsPredicate' — dimension keys have no ordering while they are predicate objects. The canonical sort is downstream of the atom rekey, not independent of it, which is one more reason that rekey is the first step rather than a cleanup.

What the design preserves, each of it live corpus behaviour: 300 basis_point == 3 percent, 155000 usd_cent being Decimal('1550.00') usd, and inches addable to metres. All three survive because the object keeps its own equality and normalises at construction. A tuple quantity carrying a ratio would have broken all three at once.
