  The headline findings:

  One rotten root causes the two worst bugs. The determinism classifier in
  tro.py (_is_deterministic_op_ir + _DETERMINISTIC_BUILTINS) claims X in L
  (membership), reified If (which explores both arms when undetermined),
  atom_concat/3, and sub_atom/5 are deterministic. They aren't, and two
  optimisations trust it:
  - A03-F001 (TRO): tail-recursion optimisation keeps only the last prefix
  solution — a recursion with X in [1,2] before the tail call returns 1 solution
  instead of 4. The shallow-compiled twin (your differential oracle) returns
  the correct set.
  - A03-F002 (destructive reuse): worse — the untrailed in-place append mutation
  survives backtracking, so the second solution is built from a corrupted list:
  [1,2,10] then [1,2,20,20]. Wrong values, not just missing ones. This directly
  invalidates the safety argument in destructive_reuse_optimization_issue.md
  §6.

  A03-F003 is a hard crash: an indexed predicate whose default bucket holds only
  a signal-mode TRO clause compiles to a function with no yield — not a
  generator — so the first dispatch to it raises TypeError. It needs ≥4 clauses
  to trigger, which is why the in-tree 3-clause fixtures never hit it.

  A03-F004 breaks the documented exception idiom: catch(..., kab(N), ...) with a
  -private-declared functor never catches, because the catcher is lowered to a
  Compound while the throw site builds the functor-class instance, and those
  don't unify. String/int/var catchers work, which is why existing tests never
  noticed.

  Specialization has three independent bugs (F007–F009): mid-body MI goals are
  silently dropped (a depth-guard MI specializes into an unguarded one), deep
  unfolding inlines single-clause functors without checking constant args (g :- 
  f(2) succeeds against a program containing only f(1)), and CPD+counting emits
  duplicate Evaluate targets so all multi-hop solutions vanish.

  Also: setof doesn't sort (F005), findall shares free template variables so
  later bindings retroactively mutate collected results (F006), and the compiler
  README still claims continuation-TCO doesn't exist (F010 doc-drift).
  Continuation-TCO itself probed clean across all its gates — wrappers, Or-arms,
  ITE arms, deferred-head-pattern output mode, exceptions through TCO'd chains.
