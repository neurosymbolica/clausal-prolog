# L3: cyclic unify is fixed only for `=`/2, `\=`/2, `is`/2 — not for
# partial-list cycles, compiled head unification, or `member`/2

Filed 2026-10-15, from the design review of `fix/is-type-check-and-cyclic-
unify-2026-10-15` (`clausal/logic/builtins/iso_compare.py::_cycle_unify`).
OPEN, not fixed by this branch.

## What the fix covers

`_cycle_unify` (and its slow-path fallback, `_cycle_unify_walk`) makes
exactly THREE call sites — the quoted canonical `'='`/2, `'\='`/2, and
`is`/2's own result-unification step, all in `iso_compare.py` — survive a
cyclic/self-referential term that is built directly through a COMPOUND
CELL (`('f', X, Y, ...)`, e.g. the Ciao `iso_tests` `unify_test16` /
`not_uni_test15` cases this branch was written for: `X = f(X)`, then
unifying two such cyclic terms). Every case in that shape now terminates
with the Ciao-asserted / Scryer-matching outcome instead of raising
`RecursionError: unify: term nesting too deep`.

## What it does NOT cover (measured, review probe `cyc.pl`)

The fix is scoped to three builtins; the underlying engine `unify()` (the
C extension, `clausal/logic/variables/_variables.c`) still has the SAME
depth-capped recursive walk everywhere else, so a cycle reached through any
OTHER path still raises. Base, 6915c42d and this branch all raise
`RecursionError` (Scryer answers `yes`) for:

```prolog
X = [a|X], Y = [a|Y], X = Y                    % partial-list cycle (SegList,
                                                % delegated to the engine's C
                                                % unify from inside this
                                                % branch's own walk too)
X = [a|X], Y = [a,a|Y], X = Y
X = [a,b|X], Y = [a|Z], Z = [b|Y], X = Y
X = f(X), Y = f(Y), same(X, Y)                 % same(A, A).  COMPILED HEAD
                                                % unification — a different
                                                % code path from '='/2/'\='/2
X = f(X), Y = f(Y), member(X, [Y])             % member/2 (library predicate,
                                                % itself compiled head
                                                % unification + '='/2 calls
                                                % that individually ARE
                                                % covered, but the cyclic
                                                % pair here is built BEFORE
                                                # member/2 is called, so the
                                                # crash is inside member/2's
                                                # own clause dispatch, not
                                                # reachable from this fix)
```

The commit message on the branch's first commit ("plain unify survives a
cyclic term") overstates this: it reads as if plain `unify` in general were
now cyclic-safe, when only the three listed call sites are. Corrected going
forward in the second commit's message; this file is the durable record of
the gap, not a correction of history.

## Why these are out of scope here

* **Partial-list cycles** go through `SegList.__unify__`, which (per
  `51f4e844`'s own fix for `==`/2) has its own cycle-reading machinery for
  WALKING a partial list (`_walk_raw`, `_CyclicPartialList`), but its
  `__unify__` hook itself still delegates structural comparison to the
  engine's recursive `unify()`/`do_unify`, which has no seen-pairs memo.
  `_cycle_unify`'s own slow walk (`_cycle_unify_walk`) delegates to the
  SAME engine `unify()` for any pair it does not itself recognise as a
  dataclass term instance, a compound cell, or a plain `list` — and a
  SegList is none of those, so it falls through to the same crash, even
  from INSIDE this branch's own fallback.
* **Compiled head unification** (`same(A, A).` matching `same(X, Y)`) is a
  totally different code path — pattern matching generated by the clause
  compiler (`clausal/logic/compiler/`), not a call to `'='`/2's builtin or
  to `_cycle_unify` at all. Confirmed unreachable: `grep -rn _cycle_unify
  clausal/ --include='*.py'` finds only `iso_compare.py`'s own three
  builtins.
* **`member`/2** is a library predicate whose own clauses do their work via
  compiled head unification and ordinary `=`/2 calls; the `=`/2 calls
  individually route through `_cycle_unify` and are themselves safe, but
  the RecursionError here comes from the COMPILED clause-head matching
  `member`/2's own definition performs when dispatching `member(X, [Y])`
  against its clauses — the same gap as the previous bullet, reached
  through a library predicate instead of user code.

## What closing this would take

Either (a) teach the ENGINE's `unify`/`do_unify` (the C extension) a
seen-pairs cycle memo directly — an engine-wide change, the operator's
call, matching the scope boundary `todo/iso-unify-conflates-int-and-float-
2026-09-09.md` already draws for narrowing `unify` itself — which would
also close the compiled-head-unification and `member`/2 gaps for free
(both bottom out in the same C function), or (b) give the clause compiler
and `SegList.__unify__`'s own fallback the SAME `_cycle_unify`-style
try-fast-then-walk treatment at each of their own call sites, which is
narrower per-site but does not share machinery with (a) and would need
separately proving safe at each site (the compiled-head-matching path in
particular has its own trail/backtracking discipline that would need the
same rollback care `_cycle_unify`'s own fallback needed, per L1 of the
same review).

Not blocking: every one of these inputs already raised `RecursionError`
before this branch (nothing regresses), and none of the ISO suite's
currently-asserted cases need them.
