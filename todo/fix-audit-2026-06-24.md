# Audit: the two 2026-06-24 fixes + bug-class follow-ups

Audit requested after landing two fixes on branch
`fix/transitive-py-backed-module-import`:

- `e9734f5f` — transitive py-backed module import (`import_hook.py`)
- `98fbb0a5` — query-cache value-keying (`solve.py`)

Verdict up front: **both fixes are correct and their regression tests are
honest.** Neither is a smell-free root-cause fix, though — each compensates for
a deeper design/packaging issue. Details + the broader classes below.

---

## Fix 1 — `_ensure_source_modules_on_path()` (import_hook.py)

**What it does:** at hook-install time, splices the source `clausal/modules`
dir onto `clausal.modules.__path__` so the source-only `py/` subpackage is
discoverable regardless of cwd.

**Is it hacky?** It's a *pragmatic runtime band-aid over a packaging defect.*
The true root cause is the install layout: `clausal_torch`/`clausal_jax` are
installed **non-editably** and drop bare `.py` files into
`site-packages/clausal/modules/` (no `__init__.py`), creating a PEP 420
namespace portion that `PathFinder` resolves *before* setuptools' editable
finder (which is *appended* to `meta_path`, so it runs last).

Caveats / sharp edges of the fix:
- Relies on CPython `_NamespacePath` accepting `insert`/`append` of a sticky
  entry — an implementation detail (observed: source lands *last*, so on a
  name collision the site-packages copy would win; no collisions exist today
  because `py/` is source-only and `torch`/`jax` wrappers are site-only).
- Eager `import clausal.modules` at hook load (light `__init__`, negligible
  startup cost — but note `implementation_plans/STARTUP_LATENCY.md`).
- It's the **third** accreted import band-aid alongside `_preseed_py_submodules`
  and `ModulesFinder` — see class A below.

**Cleaner alternatives (not done):** (a) fix packaging so extension packages
don't create a shadowing physical namespace dir / install clausal so source
wins; (b) a dedicated `clausal.modules` meta_path finder instead of mutating
`__path__`. The runtime splice was chosen as the smallest change that survives
arbitrary install layouts.

## Fix 2 — value-keyed query cache (`_structural_key`, solve.py)

**What it does:** the query cache key now encodes ground argument *values*
(recursively), distinguishes aliased vs distinct vars by first-occurrence
index, declines to cache unhashable-ground-leaf goals, and is FIFO-bounded.

**Is it hacky?** The fix itself is clean and even closes a latent var-aliasing
collision (`p(V,V)` vs `p(V,W)`). But it treats a **symptom of a design smell**:
`_compile_as_query` **bakes ground arguments into the generated code as literal
constants**. That is *why* values must be in the key, and it means every
distinct ground value triggers a **full predicate recompile** — the cache only
ever helps exact-repeat queries, and needed the new size bound to stay
bounded.

**The real fix (deferred, bigger):** lift ground args to runtime parameters
(bind them like the user's `Var`s via globals) instead of baking literals. Then
one compiled function per arg-*type* shape is reused across all values — a
type-keyed cache becomes both correct *and* compact, and the FIFO bound is
unnecessary. Tracked as class B below.

## Bug classes worth focused audits

### A. Import / module-resolution robustness  (partially tracked)
The import layer fights CPython's import machinery with a growing set of
targeted patches: `ModulesFinder` (pytest `py` shim), `_preseed_py_submodules`
(stale `sys.modules["py"]`), and now `_ensure_source_modules_on_path`
(namespace shadow). Each is correct in isolation; together they signal the
resolution model is fragile. **Audit:** enumerate the invariants the import hook
needs (cwd-independence, install-layout-independence, `sys.modules` pollution
tolerance, editable-vs-namespace coexistence) and cover each with a subprocess
test matrix, then consider consolidating the band-aids behind one finder.

### B. Compile-time literal-baking → per-value recompilation  (NEW) — FIXED (targeted)
> **Resolved for the dominant case.** Measured cost first: querying one module
> with distinct ground values recompiled per value at ~452 µs/query — **19×**
> slower than a cache hit (~23 µs). Fix: `solve()` now parameterizes the
> **scalar** ground top-level args of a predicate-call goal — each is replaced
> with a fresh Var (`_templatize_query_goal`) and bound to its value on the trail
> before driving — so the compiled query is value-independent and the structural
> cache key matches across values. Result: 2000 distinct-valued queries now use
> **one** compiled query at ~24 µs/query (cache-hit speed).
>
> Scope/limits (deliberate, for safety): only scalar literals
> (int/float/complex/bool/str/bytes/None) are parameterized — they unify directly
> with head literals in any mode. Structural args (list/dict/compound) are *not*
> (the literal-baking path rewrites them, e.g. list→cons), and composite/control/
> arithmetic goals are untouched; both keep the value-keyed cache + FIFO bound
> from Fix 2 as a correct fallback (so that machinery stays, contrary to the
> original "retire it" note). Regression test:
> `tests/test_query_arg_parameterization.py` (reuse + multi-solution + interleave).
> Follow-up (optional): extend parameterization to structural args by binding the
> cons/dict-rewritten value, and descend And/Or to parameterize nested calls.
> A residual audit item remains: check whether the same constant-folding bloats
> *clause-body* compilation (`term_to_ast_expr` call sites) beyond query goals.

### C. Low-level DB-mutation API does not sync the predicate class  (NEW, minor) — FIXED
> **Resolved.** `Database.assertz/asserta/retract` now mirror the clause-list
> change onto the matching (unlocked) `PredicateMeta` class found via
> `self.module_dict`, so `solve()` sees low-level mutations. The redundant
> explicit class syncs in the `assertz/1`/`asserta/1` builtins and the three
> `specialization.py` install sites were collapsed onto this single path
> (locked/static predicates are skipped so the lock isn't bypassed). Regression
> test: `tests/test_low_level_db_mutation_sync.py`.

`Database.assertz/asserta/retract` update `db._clauses` and invalidate
`db._dispatch[key]`, but do **not** sync the predicate class's `_clauses` /
dispatch. The `assertz/1` *builtin* does (Phase 8c). Consequence: code that
embeds clausal and calls `db.assertz(...)` directly, then runs `solve()` of
that predicate, sees **stale** results (compiled query resolves the call target
through the class). The supported `.clausal` `assertz/1` goal path is correct
(verified: clause visible within the query and to a later independent solve).
**This bit the audit's own probe.** Fix: make the low-level `Database` mutators
perform the same `pred_cls` sync as the builtin, or document that `db.*` are
internal and route embedders through the builtin/a public API.
